# 개발 컨벤션

## 1. 문서 목적

본 문서는 팀원이 같은 기준으로 브랜치, 커밋, Pull Request, 코드 작성, 보안 점검, 작업 분리를 진행하기 위한 개발 컨벤션을 정의한다.

서비스 기능, API, DB, 인증·권한, AI Worker, 배포 구조에 대한 세부 기준은 각 설계 문서를 우선한다.

---

## 2. Git 브랜치 전략

### 2.1 기본 브랜치

- `main`: 최종 제출 또는 배포 가능한 안정 브랜치
- `develop`: 개발 통합 브랜치

### 2.2 브랜치 운용 규칙

- 모든 작업은 `develop` 브랜치에서 분기한 작업 브랜치에서 진행한다.
- `main` 브랜치에는 직접 push하지 않는다.
- 작업 완료 후 Pull Request를 생성하고, 확인 후 `develop` 브랜치로 병합한다.
- 최종 제출 또는 배포 시 `develop`에서 `main`으로 병합한다.

### 2.3 작업 브랜치 규칙

브랜치 이름은 `작업유형/작업내용` 형식으로 작성한다.

사용 가능한 작업 유형은 다음과 같다.

| 유형 | 설명 |
| --- | --- |
| `feat` | 새로운 기능 개발 |
| `fix` | 버그 수정 |
| `refactor` | 리팩토링 |
| `docs` | 문서 작업 |
| `chore` | 설정, 의존성, 빌드 등 기타 작업 |
| `test` | 테스트 코드 작성 및 수정 |
| `hotfix` | 긴급 수정 |
| `release` | 배포 전 최종 점검 |

예시:

```
feat/image-upload
feat/analysis-job
fix/login-redirect
docs/development-convention
chore/local-docker-setup
```

## 3. 커밋 메시지 규칙

### 3.1 기본 형식

커밋 메시지는 `type: 작업 내용` 형식으로 작성한다.

```
type: 작업 내용
```

### 3.2 커밋 타입

| 타입 | 설명 |
| --- | --- |
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 |
| `refactor` | 기능 변화 없는 코드 구조 개선 |
| `test` | 테스트 추가 또는 수정 |
| `chore` | 빌드, 설정, 의존성, 환경 관련 작업 |

### 3.3 커밋 예시

```
feat: 이미지 업로드 API 구현
fix: 로그인 후 승인 대기 화면 이동 오류 수정
docs: 개발 컨벤션 문서 추가
chore: 로컬 Docker 설정 정리
test: 분석 작업 생성 테스트 추가
```

### 3.4 커밋 작성 기준

- 커밋은 가능한 한 하나의 목적만 담는다.
- 변경 내용을 한눈에 파악할 수 있게 작성한다.
- 의미가 불분명한 메시지는 사용하지 않는다.

## 4. Pull Request 규칙

### 4.1 PR 생성 기준

- 모든 기능 개발 및 수정 작업은 브랜치 단위로 진행한 뒤 Pull Request를 생성한다.
- PR은 가능한 한 기능 단위로 작성한다.
- 너무 큰 단위의 변경은 지양하고, 리뷰 가능한 크기로 나누어 올린다.

### 4.2 PR 제목

PR 제목은 `[type] 작업 내용` 형식으로 작성한다.

예시:

```
[feat] 이미지 업로드 기능 구현
[fix] 분석 상태 조회 오류 수정
[docs] 개발 컨벤션 문서 추가
[chore] 로컬 DB 설정 정리
```

### 4.3 PR 본문

PR 본문에는 아래 내용을 포함한다.

```markdown
## 관련 작업
-

## 작업 내용
-

## 주요 변경 사항
-

## 테스트/검증 내용
- [ ] 기능 동작 확인
- [ ] 예외 케이스 확인
- [ ] 빌드 또는 테스트 통과
- [ ] 추가 확인 필요

## 참고 사항
-
```

### 4.4 PR 체크리스트

PR 생성 전 아래 항목을 확인한다.

- 현재 작업 브랜치가 올바른지 확인한다.
- 변경 범위가 작업 목적과 직접 관련 있는지 확인한다.
- 불필요한 코드, 주석, 콘솔 로그를 제거한다.
- 커밋 메시지가 규칙에 맞는지 확인한다.
- PR 본문에 작업 내용과 검증 내용을 정리한다.
- 기능이 정상 동작하는지 직접 확인한다.
- 민감 정보가 포함되지 않았는지 확인한다.
- merge 충돌 가능성이 없는지 확인한다.

## 5. 코드 네이밍 기준

### 5.1 공통 기준

- 이름은 역할이 드러나도록 작성한다.
- 축약어는 과하게 사용하지 않는다.
- 의미가 불분명한 이름은 사용하지 않는다.
- 기존 코드의 네이밍 스타일을 우선 따른다.

### 5.2 Java / Spring Backend

- 클래스명은 PascalCase를 사용한다.
- 메서드명과 변수명은 camelCase를 사용한다.
- 패키지명은 소문자 기준으로 작성한다.
- 상수는 UPPER_SNAKE_CASE를 사용한다.
- DTO, Command, Query, Response, UseCase, Port, Adapter 등은 역할이 이름에 드러나도록 작성한다.

예시:

```
CreateInspectionCommand
InspectionResponse
RequestAnalysisUseCase
AnalysisJobRepositoryPort
SqsAnalysisJobPublisherAdapter
```

### 5.3 React / TypeScript Frontend

- 컴포넌트명은 PascalCase를 사용한다.
- 함수명, 변수명, hook 이름은 camelCase를 사용한다.
- React hook은 `use`로 시작한다.
- API 요청 함수는 동작과 대상이 드러나도록 작성한다.

예시:

```
InspectionDetailPage
ImageUploadForm
useAnalysisJobStatus
fetchInspectionResults
```

### 5.4 Python / AI Worker

- 파일명, 함수명, 변수명은 snake_case를 사용한다.
- 클래스명은 PascalCase를 사용한다.
- 상수는 UPPER_SNAKE_CASE를 사용한다.
- 모델, 전처리, 후처리, 저장소, Queue 처리 역할이 이름에 드러나도록 작성한다.

예시:

```
analysis_worker.py
model_router.py
load_rgb_image
run_onnx_inference
save_visualization_result
```

## 6. 주석 작성 기준

- 코드만으로 의도가 분명하면 주석을 작성하지 않는다.
- 주석은 코드가 무엇을 하는지보다 왜 그렇게 처리하는지를 설명한다.
- 복잡한 비즈니스 규칙, 권한 조건, 예외 처리 이유는 주석으로 남긴다.
- 임시 주석이나 TODO는 남발하지 않는다.
- TODO를 남길 경우 이유와 후속 작업을 명확히 적는다.
- 오래된 주석이나 실제 코드와 맞지 않는 주석은 수정하거나 제거한다.

예시:

```java
// Pair 분석은 동일 점검, 동일 검사 대상의 RGB/THERMAL 이미지가 모두 있을 때만 허용한다.
```

## 7. 보안 기준

- Secret, API Key, DB 비밀번호, OAuth Client Secret은 코드에 직접 작성하지 않는다.
- 실제 Secret 값이 들어간 `.env`, `.yml`, `.json` 파일은 커밋하지 않는다.
- `.env.example`에는 키 이름과 설명만 작성한다.
- 인증과 권한 검증은 Backend를 최종 기준으로 적용한다.
- 일반 사용자는 본인이 생성했거나 접근 권한이 있는 데이터만 조회·수정할 수 있다.
- 로그에 Secret, 토큰, 개인정보, Presigned URL 등을 남기지 않는다.
- 원본 이미지와 분석 결과 이미지 접근은 인증 및 권한 검증을 거쳐야 한다.

## 8. 작업 분리 및 겹치는 범위 처리 기준

본 프로젝트는 기능별 병렬 구현을 위해 작업 소유 범위를 구분한다.

각 팀원은 본인 소유 범위를 우선 담당하되, 다른 팀원 소유 범위의 기능이 필요한 경우 직접 구현하지 않고 정해진 인터페이스나 공통 컴포넌트를 호출한다.

### 8.1 최종 분리 기준

```
팀원 1:
인증 / 권한 / 사용자 / 발전소 / 구역 / 하위 설비 / 공통 접근 제어 / 공통 운영 설정

팀원 2:
점검 / 이미지 / RGB-Thermal Pair / 분석 Job / 분석 결과 / 대시보드 / Storage / Queue / Worker Contract
```

### 8.2 겹치는 범위 처리 기준

| 겹치는 상황 | 최종 소유자 | 처리 방식 |
| --- | --- | --- |
| 권한 검증 | 팀원 1 | 팀원 1이 AccessChecker 구현, 팀원 2는 호출만 함 |
| Zone / Equipment 조회 | 팀원 1 | 팀원 2는 점검/이미지 생성 시 검증용으로 사용 |
| ImagePair 생성 | 팀원 2 | Pair 후보 조회, 생성, 수정, Fusion 입력 검증 담당 |
| AnalysisJob 생성 | 팀원 2 | Job 생성, 재시도, SQS 메시지 발행 담당 |
| Dashboard / Admin 조회 | 팀원 2 중심 | 분석 결과 기반 집계는 팀원 2, 사용자 관리는 팀원 1 |
| DB Migration 충돌 | 공동 작업 | 최종 반영 담당자 1명 지정 |

### 8.3 작업 시 주의 사항

- 각 팀원은 본인 소유 범위의 UseCase, Port, DTO, Service, Adapter, Controller 작업을 우선 담당한다.
- 다른 팀원 소유 범위의 기능이 필요한 경우 직접 구현하지 않고, 기존 인터페이스나 공통 컴포넌트를 호출한다.
- 소유 범위가 겹치거나 DB Migration 충돌이 예상되면 작업 전에 최종 반영 담당자를 정한다.
- 인증, 권한, DB 구조, API 구조, Queue, Storage, Worker Contract는 임의로 변경하지 않는다.
- 작업 중 소유 범위 밖의 수정이 필요하면 PR 본문 또는 작업 보고에 남긴다.

## 9. 제출 전 점검 기준

작업 완료 전 아래 항목을 확인한다.

- 요청한 작업 범위만 수정했는지 확인한다.
- 관련 없는 대규모 리팩토링을 하지 않았는지 확인한다.
- API, DB, 인증, 권한, 배포 구조를 임의로 바꾸지 않았는지 확인한다.
- 빌드 또는 테스트를 가능한 범위에서 실행한다.
- 실행하지 못한 테스트는 PR 본문에 명시한다.
- 임시 파일, 로그 파일, 빌드 산출물, 디버깅 코드를 제거한다.
- 문서 기준과 실제 코드가 다르면 PR 본문에 남긴다.
- 남은 이슈나 확인 필요한 사항을 숨기지 않고 작성한다.

## 10. 결론

본 컨벤션은 팀원이 같은 기준으로 브랜치, 커밋, PR, 코드 작성, 보안 점검, 작업 분리를 진행하기 위한 최소 기준이다.

서비스 기능, API, DB, 인증·권한, AI Worker, 배포 구조에 대한 세부 기준은 각 설계 문서를 우선한다.

컨벤션과 설계 문서가 충돌할 경우 설계 문서를 우선 확인하고, 필요한 경우 팀 내 합의 후 컨벤션을 수정한다.
